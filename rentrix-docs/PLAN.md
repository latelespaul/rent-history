# Rentrix v1 — Implementation plan (PR sequence)

Status: **current**. Date: 2026-11-21. Revised 2026-11-21 (design v2): data-driven cities (C1, C2 — **IMMEDIATE**), verification with admin approvals (B11, B12, W8), admin console (B13, W9). Revised 2026-11-22 (**design v3**): identity verification with any one of Aadhaar, PAN or phone OTP and LinkedIn as an optional badge (**B14**, changes B11, B12, W8), location hierarchy City → Area → Society → Tower → Wing → Unit (**B15**, changes B4), roll-ups and browse by area / society / owner (**B16**, **W10**). Rows changed by v3 are marked *(v3)*.
Source of truth for behaviour: [`architecture/SYSTEM_DESIGN.md`](architecture/SYSTEM_DESIGN.md) (decisions `D-xx`).
This file only orders the work. If a PR must deviate from the design, it updates SYSTEM_DESIGN.md in the same PR and says why.

## Rules for every PR

- Small and reviewable alone; master stays green after each merge (backend tests, web lint/build/test, migrations).
- Branch from latest `master`; one concern per PR; passes no-mistakes before merge.
- Backend tests run on the **real Flyway migrations** (SQLite by default; MySQL/Postgres via Testcontainers in CI from O2 on).
- Google is never called in tests: `FakeGoogleTokenVerifier` (D-75).
- Every UI PR body has: run command(s), URL, test logins (dev-login seed users, D-77), the pages to shoot, and the screenshots. Images are also committed to `rentrix-docs/screenshots/<pr-id>/` (`git add -f`, the root `.gitignore` ignores `rentrix-docs/`).
- Screenshots come from a local headless browser (Playwright) against local dev servers only.
- No invented numbers or testimonials anywhere (D-03). No hard-coded city list, city name or "only these cities" copy anywhere in API or web: cities come from `GET /cities` (D-20, D-85). Launch cities are Bangalore and Pune; more are added as data.

## Tracks

- **B** backend (`rentrix-server`), **W** web (`rentrix-web`), **O** ops/CI, **S** screenshots, **C** cities fix (one backend + one web PR, **IMMEDIATE**: they go before every other open item in their track).
- Done: **B1 backend core** (#17), **UX design** (#16), **W1 web reset** (#19), **design v2** (#21), **B2 common API layer** (#22), **O1 Docker** (#18), **C1 data-driven cities** (#23), **C2 city picker** (#24). **B3 auth** is being built now.
- **Design v3** (this revision) is the design PR for B14, B15, B16, W10 and for the *(v3)* changes in B4, B6, B10–B13, W2, W4, W6, W8 and W9. Its decisions are D-99–D-115; tables and migrations are in [`database/schema.md`](database/schema.md).

## Order and parallelism

```
IMMEDIATE:  B1 ─▶ C1 ;  W1 + C1 + design v2 ─▶ C2

B1 ─▶ B2 ─▶ B3 ─▶ B14 ─▶ B11 ─┬─▶ B4 ─▶ B5 ─┬─▶ B6 ─┬─▶ B16 ─────────┐
        │                     │      ▲      └─▶ B7 ─┴─▶ B8 ─┐          │
        └─ C1 ─▶ B15 ─────────┼──────┘ (B4 needs B15)        │          │
                              └──────▶ B9 ─▶ B12 ────────────┴─▶ B13 ─┐ │
                                                                     ▼ ▼
design v2 + design v3 ─┐                                           B10 ─┐
B1 ─▶ W1 ─▶ C2 ─▶ W2 ─▶ W3 ─┬─▶ W4 ─────────────┐                       │
                            ├─▶ W5 (needs B5, B9)│                      ├─▶ O3 ─▶ S1
                            ├─▶ W6 (needs B6, B7)┴─▶ W10 (needs B16)    │
                            ├─▶ W7 (needs B8)                           │
                            ├─▶ W8 (needs B11, B12, B14)                │
                            └─▶ W9 (needs B13)                          │
B1+W1 ─▶ O1 ;  B2+W1 ─▶ O2 ─────────────────────────────────────────────┘
```

- **C1 and C2 are IMMEDIATE.** C1 needs only B1 (merged), so it is the next backend PR and runs beside B2. C2 is the first W PR after W1; W2 builds the shell on its picker. Until C2 merges, no web PR may add a city toggle or city literal.
- Backend critical path B1→B3→B14→B11→B4→B5→B6. **Design v3 slots in after B3** (auth, being built now): B14 needs B3's `/me` and JWT filter and is the next backend PR after it, then B11, whose submit and approve rules read B14's identity rows, so B4–B7 call `ApprovalGuard` (approval + ID verified) as they are built instead of being retrofitted. B15 needs only B2 (merged) and C1, so it can run beside B3 and B14; B4 waits for it so properties are created with an area from the first row. B16 follows B6 (it extends B6's recompute hook). B6/B7, then B8/B12, can run in parallel; B13 needs both B8 and B12.
- W1 can start as soon as B1 is merged; O1 after B1 + W1; O2 after B2 + W1. W2 starts when the UX design PR is merged.
- W PRs can be built against a dev server while their backend PR is open, but merge only after it (master stays green).
- Seed (B10) lands before the UI PRs need rich data for screenshots; until then UI PRs screenshot with data created through the dev API. If B10 is late, W4–W7 may merge with interim screenshots and S1 re-shoots.

## Notes

- **Google sign-in** is B3 (API, README steps) + W3 (UI). Dev login keeps local runs, tests and screenshots Google-free.
- **Fake claims**: removed in W1 (HomePage stats, testimonials, "18 cities"); W4 rebuilds Home on `/stats` only.
- **Migrations**: B1 owns `V1` (frozen). B2 (merged) added `V2__idempotency_keys.sql`. Design v2 adds three migrations: cities (C1, `V3__city_pincode_prefixes.sql`), verification core (B11, plus the `moderation_actions` rebuild) and verification documents (B12, `verification_documents`); each takes the next free version when its PR merges (D-98). Design v3 adds two: identity (B14, `identity_verifications` + `phone_otp_challenges`) and location (B15, five tables + four `properties` columns + a MySQL vendor FK file), and changes the not-yet-merged B11 and B12 DDL (D-114, [`database/schema.md`](database/schema.md)). No PR edits a merged migration.
- **Cities**: adding a city is a DB row plus admin activation (D-83); no PR adds a city to code.
- **Approvals**: reading never needs approval; trust writes do (D-91), and from design v3 they also need an ID-verified user (D-105). Tests for B4–B7 create approved, ID-verified users through a test fixture; the seed (B10) approves every seeded party.
- **Identity** (design v3): verified = any one of Aadhaar (masked copy, last 4 only), PAN or phone OTP; LinkedIn is an optional badge (D-99, D-100). No PR stores, logs or returns a full PAN, a full Aadhaar number or an OTP code (D-106). SMS is never sent in tests (`LogSmsSender`).
- **Location** (design v3): every property has an area; society, tower and wing are optional (D-107–D-110). Seed: one gated society per city with 2 towers × 2 wings (D-115).
- **Privacy**: no API, log, email or screenshot may contain a full ID number; screenshots use the seed's placeholder documents only (D-94, D-95, D-97).
- **Seed** is dev-only code (B10), never a Flyway migration.
- **Screenshot run recipe** (every UI PR): `SPRING_PROFILES_ACTIVE=dev SEED_DEMO=true ./mvnw spring-boot:run` in `rentrix-server`, `npm run dev` in `rentrix-web`, open `http://localhost:5173`, sign in via the dev-login picker (e.g. "Demo Landlord BLR-1", "Demo Tenant PNQ-3", `demo-admin@example.test`; for approval states "Demo Landlord BLR-3" pending, "Demo Tenant BLR-8" rejected). Stop both servers and the headless browser afterwards.
