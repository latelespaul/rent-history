## Rules for every PR

- Small and reviewable alone; master stays green after each merge (backend tests, web lint/build/test, migrations).
- Branch from latest `master`; one concern per PR; passes no-mistakes before merge.
- Backend tests run on the **real Flyway migrations** (SQLite by default; MySQL/Postgres via Testcontainers in CI from O2 on).
- Google is never called in tests: `FakeGoogleTokenVerifier` (D-75).
- Every UI PR body has: run command(s), URL, test logins (dev-login seed users, D-77), the pages to shoot, and the screenshots. Images are also committed to `rentrix-docs/screenshots/<pr-id>/` (`git add -f`, the root `.gitignore` ignores `rentrix-docs/`).
- Screenshots come from a local headless browser (Playwright) against local dev servers only.
- No invented numbers or testimonials anywhere (D-03). No hard-coded city list, city name or "only these cities" copy anywhere in API or web: cities come from `GET /cities` (D-20, D-85). Launch cities are Bangalore, Pune, Mumbai, Hyderabad and Delhi NCR (Delhi, Gurugram, Noida), from `V8__launch_cities.sql`; more are added as data.

## Tracks

- Rows keyed **R**, **U** or **P** plus a number are items from the captain's feedback tracker, under the tracker's own ID.
- **B** backend (`rentrix-server`), **W** web (`rentrix-web`), **O** ops/CI, **S** screenshots, **C** cities fix (one backend + one web PR, **IMMEDIATE**: they go before every other open item in their track).
- Done: **B1 backend core** (#17), **UX design** (#16), **W1 web reset** (#19), **design v2** (#21), **B2 common API layer** (#22), **O1 Docker** (#18), **C1 data-driven cities** (#23), **C2 city picker** (#24), **W2 shell** (#27), **B3 auth** (#26), **B4a properties** (#28), **B14 identity verification core** (#29), **W4a home, search, property page** (#32; see the W4 row), **B15 location hierarchy** (#33; it also brings B4b's `GET /properties` location filters), **W3 sign-in + role pick** (#30), **B5 tenancies + rent records** (#34), **B11 verification core** (#35), **B6 reviews + aggregates** (#36). **W5a landlord properties + tenancies** (see the W5 row; it also brings B4b's `location` on property create / edit, without the gates). **B5 tenancies + rent records** is built before B11 with an interim approval gate (see Notes, "Interim approval gate"). **B4 is split**: B4a (properties, search, stats, minimal dev seed) ships first so the demo has homes to browse; B4b adds the location hierarchy fields on create / edit and the listing gates once B11, B12 and B15 merge. Rows that depend on B4 need B4a unless they use location or the gates.
- **Design v4** (this revision) is the design PR for B17, the pulled-forward W8 and B18. Its decisions are D-116–D-131 (SYSTEM_DESIGN §7.5, §7.6, §5.20); the table is in [`database/schema.md`](database/schema.md) §6; mockups are the *(v4)* rows of [`design/DESIGN.md`](design/DESIGN.md) §3. Order: design v4 → **B17 + W8** (one PR, because the captain tests the whole sign-in flow together, with a minimal landing) together with **B13 queue slice + W9 approvals** → **B19 + W11** landlord / tenant add flows → **B18** agreement anchor checks. *(v4, open by default)* adds D-132–D-137 (SYSTEM_DESIGN §7.7) and the verification-state migration ([`database/schema.md`](database/schema.md) §7). **Launch readiness** = landing + sign-up rework (B17 + W8) + landlord / tenant add flows (B19 + W11) + W9 approvals + the live-mode switch (`PREVIEW_MODE` off, `SMS_BACKEND=http` with a real SMS provider). ## Notes

- **Google sign-in** is B3 (API, README steps) + W3 (UI). Dev login keeps local runs, tests and screenshots Google-free.
- **Fake claims**: removed in W1 (HomePage stats, testimonials, "18 cities"); W4 rebuilds Home on `/stats` only.
- **Migrations**: B1 owns `V1` (frozen). B2 (merged) added `V2__idempotency_keys.sql`. Design v2 adds three migrations: cities (C1, `V3__city_pincode_prefixes.sql`), verification core (B11, plus the `moderation_actions` rebuild) and verification documents (B12, `verification_documents`); each takes the next free version when its PR merges (D-98). Design v3 adds two: identity (B14, `identity_verifications` + `phone_otp_challenges`) and location (B15, five tables + four `properties` columns + a MySQL vendor FK file), and changes the not-yet-merged B11 and B12 DDL (D-114, [`database/schema.md`](database/schema.md)). No PR edits a merged migration.
- **Cities**: adding a city is a DB row plus admin activation (D-83); no PR adds a city to code.
- **Approvals**: reading never needs approval; trust writes do (D-91), and from design v3 they also need an ID-verified user (D-105); *(v4)* from B17 that means a verified phone (D-117). *(v4, open by default)* From B17 trust writes need only the verified phone; approval gives the green tick (D-132, D-134). Tests for B4–B7 create approved, ID-verified users through a test fixture; the seed (B10) approves every seeded party.
- **Interim approval gate (built in B5, replaced by B11)**: B5 shipped `verification/ApprovalGuard.require(user, role)` with interim statuses (every held role `DRAFT`, demo users `APPROVED`). B11 replaced them with `VerificationService` reading `verification_applications`, added the ID-verified half (`403 id_verification_required`, D-105), made `TestData.approved` write an approved application plus a verified phone check, and has the dev seed write approved applications for the demo users. The B5 call sites are unchanged.
- **Identity** (design v3): verified = any one of Aadhaar (masked copy, last 4 only), PAN or phone OTP; LinkedIn is an optional badge (D-99, D-100). *(v4)* Phone OTP is required for everyone; PAN / masked Aadhaar are optional extra badges (D-117). A deployment without an SMS sender (`prod` with no `SMS_BACKEND`, as in the root `docker-compose.yml` today) cannot verify phones. The preview runs `SMS_BACKEND=admin-relay` with `PREVIEW_MODE=true` (B17, D-137): an admin reads the pending code in the approvals queue and passes it on, so real Google sign-ups on the preview can verify a phone and post. A real SMS provider is a launch item under the live-mode switch (`PREVIEW_MODE` off, `SMS_BACKEND=http`); demo users are seeded with a verified phone. No PR stores, logs or returns a full PAN, a full Aadhaar number or an OTP code (D-106; the admin-relay code is shown to admins only, in memory, D-137). SMS is never sent in tests (`LogSmsSender`).
- **Rental agreements** (design v4): manual field entry only, no OCR or LLM extraction, no file redaction (Aadhaar inside files is protected by encryption, access rules and the delete 30 days after the later of the decision and the other party's confirmation instead), no portal scraping (D-127, D-130, D-131). Parked until the captain approves: the vision extractor.
- **Storage before B9** (design v4): B18 adds the minimal `ImageStorage` interface with only the local PRIVATE implementation; B9 later adds PUBLIC, S3 and image processing on the same interface.
- **Location** (design v3): every property has an area; society, tower and wing are optional (D-107–D-110). Seed: one gated society per city with 2 towers × 2 wings (D-115).
- **Privacy**: no API, log, email or screenshot may contain a full ID number; screenshots use the seed's placeholder documents only (D-94, D-95, D-97).
- **Co-tenants (future, not planned yet)**: a whole home holds one tenancy at a time (D-23), so two people sharing one whole-home lease cannot both record it today. The fix is several tenants as parties on one tenancy, not overlapping tenancies; `ROOM` and `PG` already take overlapping flatmate tenancies.
- **Seed** is dev-only code (B10), never a Flyway migration.
- **Screenshot run recipe** (every UI PR): `SPRING_PROFILES_ACTIVE=dev SEED_DEMO=true ./mvnw spring-boot:run` in `rentrix-server`, `npm run dev` in `rentrix-web`, open `http://localhost:5173`, sign in via the dev-login picker (e.g. "Demo Landlord BLR-1", "Demo Tenant PNQ-3", `demo-admin@example.test`; for approval states "Demo Landlord BLR-3" pending, "Demo Tenant BLR-8" rejected).
