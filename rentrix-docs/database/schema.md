# Rentrix — Database schema changes (design v3)

Status: **current**. Date: 2026-11-22.
Decisions live in [`../architecture/SYSTEM_DESIGN.md`](../architecture/SYSTEM_DESIGN.md) (`D-xx`); this file is the table reference for the design-v3 tables and the migration plan. The shipped baseline is `rentrix-server/src/main/resources/db/migration/V1__baseline_schema.sql` (frozen, D-98) plus `V2__idempotency_keys.sql`. ER diagrams: [`er-diagram.md`](er-diagram.md).

All DDL below follows the V1 conventions (D-10, D-12, D-80, D-81): portable SQL subset, `BIGINT` ids generated by the API, `public_id CHAR(36)` UUIDv7 on every externally visible row, enums as `VARCHAR` with no `CHECK` on value lists, `${timestamp_type}` for timestamps, `created_at`/`updated_at` on every table. The DDL is a design sketch; the migration PR is the source of truth for exact text.

## 2. Identity verification (D-99 – D-106)

### 2.1 `identity_verifications`

One row per user per method. "ID verified" = any row with `method IN ('AADHAAR','PAN','PHONE_OTP') AND status = 'VERIFIED'` (D-99).

```sql
CREATE TABLE identity_verifications (
    id              BIGINT            NOT NULL,
    public_id       CHAR(36)          NOT NULL,
    user_id         BIGINT            NOT NULL,
    method          VARCHAR(16)       NOT NULL,   -- AADHAAR | PAN | PHONE_OTP | LINKEDIN
    status          VARCHAR(16)       NOT NULL,   -- PENDING | VERIFIED | REJECTED | REVOKED
    last4           VARCHAR(4),                   -- PAN, Aadhaar, phone: last 4 only; null for LINKEDIN
    value_hmac      CHAR(64),                     -- HMAC-SHA256 hex of PAN or E.164 phone; null for AADHAAR, LINKEDIN
    linkedin_url    VARCHAR(200),                 -- LINKEDIN only, normalised, private
    checked_by      VARCHAR(16),                  -- ADMIN | OTP | PROVIDER
    provider        VARCHAR(40),                  -- null in v1 (D-104)
    provider_ref    VARCHAR(100),
    verified_at     ${timestamp_type},
    verified_by     BIGINT,                       -- admin user; null for OTP
    reject_code     VARCHAR(32),
    reject_note     VARCHAR(1000),
    revoked_at      ${timestamp_type},
    created_at      ${timestamp_type} NOT NULL,
    updated_at      ${timestamp_type} NOT NULL,
    CONSTRAINT pk_identity_verifications PRIMARY KEY (id),
    CONSTRAINT uq_identity_verifications_public_id UNIQUE (public_id),
    CONSTRAINT uq_identity_verifications_user_method UNIQUE (user_id, method),
    CONSTRAINT fk_identity_verifications_user FOREIGN KEY (user_id) REFERENCES users (id),
    CONSTRAINT fk_identity_verifications_verifier FOREIGN KEY (verified_by) REFERENCES users (id)
);
CREATE INDEX ix_identity_verifications_hmac ON identity_verifications (method, value_hmac);
CREATE INDEX ix_identity_verifications_queue ON identity_verifications (status, method, created_at);
```

| Method | `last4` | `value_hmac` | How it becomes `VERIFIED` |
|---|---|---|---|
| `PHONE_OTP` | last 4 digits of the phone | HMAC of E.164 phone | user confirms the SMS code (D-101) |
| `PAN` | last 4 characters | HMAC of the upper-cased PAN | admin compares the uploaded card (D-102) |
| `AADHAAR` | last 4 digits as printed on the masked copy | **none** (full number never received) | admin checks the masked copy (D-103) |
| `LINKEDIN` | none | none | admin opens the URL; bonus badge only (D-93, D-100) |

What is never in any column: a full PAN, any Aadhaar digit beyond the last 4, an OTP code (D-106).

### 2.2 `phone_otp_challenges`

```sql
CREATE TABLE phone_otp_challenges (
    id              BIGINT            NOT NULL,
    public_id       CHAR(36)          NOT NULL,   -- the challengeId returned to the client
    user_id         BIGINT            NOT NULL,
    phone_e164      VARCHAR(16)       NOT NULL,   -- private (D-57)
    phone_hmac      CHAR(64)          NOT NULL,   -- per-number send limit across accounts
    code_hmac       CHAR(64)          NOT NULL,   -- HMAC of the 6-digit code; the code is never stored
    attempts        INTEGER           NOT NULL DEFAULT 0,
    expires_at      ${timestamp_type} NOT NULL,   -- created_at + OTP_TTL_MINUTES
    consumed_at     ${timestamp_type},
    created_at      ${timestamp_type} NOT NULL,
    updated_at      ${timestamp_type} NOT NULL,
    CONSTRAINT pk_phone_otp_challenges PRIMARY KEY (id),
    CONSTRAINT uq_phone_otp_challenges_public_id UNIQUE (public_id),
    CONSTRAINT fk_phone_otp_challenges_user FOREIGN KEY (user_id) REFERENCES users (id),
    CONSTRAINT ck_phone_otp_attempts CHECK (attempts >= 0 AND attempts <= 5)
);
CREATE INDEX ix_phone_otp_user_created ON phone_otp_challenges (user_id, created_at);
CREATE INDEX ix_phone_otp_phone_created ON phone_otp_challenges (phone_hmac, created_at);
```
A locked nightly job (D-08) deletes rows 24 h after `expires_at` or `consumed_at`.

### 2.3 Changes to the not-yet-merged design-v2 tables

- `verification_applications` (B11): drop the design-v2 columns `linkedin_url`, `linkedin_not_provided`, `linkedin_check` from the planned DDL. `flags` may hold `DUPLICATE_ID` and `DUPLICATE_PHONE`. Adds `version INTEGER NOT NULL DEFAULT 0` (optimistic lock, JPA `@Version`): a concurrent decision or resubmit of the same application loses with `409 invalid_transition`. Reject codes per §5.13 of SYSTEM_DESIGN.
- `verification_events` (B11): `event` adds `IDENTITY_CHECKED` (replaces `LINKEDIN_CHECKED`).
- `verification_documents` (B12): add `identity_verification_id BIGINT` (FK `identity_verifications`, set for `ID_PROOF`); `id_type` ∈ `PAN`, `AADHAAR_MASKED`; remove `number_last4` and `number_hmac` from the planned DDL; `ID_PROOF` files are deleted when their identity check is decided, so `purge_after` is set only for `RENTAL_AGREEMENT` and `PROPERTY_PROOF` (D-96); indexes `(owner_id, kind)`, `(identity_verification_id)`, `(status, purge_after)`.
- `moderation_actions` (B11 rebuild): new `action` values `VERIFY_IDENTITY`, `REJECT_IDENTITY`, `REVOKE_IDENTITY`, `CREATE_AREA`, `UPDATE_AREA`, `APPROVE_LOCATION`, `UPDATE_LOCATION`; new `target_type` values `IDENTITY`, `AREA`, `SOCIETY`, `TOWER`, `WING`. No DDL (enum columns have no `CHECK`).

## 3. Location hierarchy (D-107 – D-110)

```
cities ─1:N─ areas ─N:N─ PIN codes (area_pincodes)
               └─1:N─ societies ─1:N─ society_towers ─1:N─ society_wings
properties ─N:1─ areas, ─N:0..1─ societies, society_towers, society_wings   (property = unit)
```

### 3.1 `areas` and `area_pincodes`

```sql
CREATE TABLE areas (
    id              BIGINT            NOT NULL,
    public_id       CHAR(36)          NOT NULL,
    city_code       VARCHAR(8)        NOT NULL,
    name            VARCHAR(120)      NOT NULL,
    name_key        VARCHAR(120)      NOT NULL,   -- lower-case, single spaces
    aliases         VARCHAR(255),
    status          VARCHAR(16)       NOT NULL,   -- ACTIVE | PENDING | HIDDEN
    created_by      BIGINT,
    is_demo         BOOLEAN           NOT NULL DEFAULT FALSE,
    created_at      ${timestamp_type} NOT NULL,
    updated_at      ${timestamp_type} NOT NULL,
    CONSTRAINT pk_areas PRIMARY KEY (id),
    CONSTRAINT uq_areas_public_id UNIQUE (public_id),
    CONSTRAINT uq_areas_city_name UNIQUE (city_code, name_key),
    CONSTRAINT fk_areas_city FOREIGN KEY (city_code) REFERENCES cities (code),
    CONSTRAINT fk_areas_created_by FOREIGN KEY (created_by) REFERENCES users (id)
);
CREATE INDEX ix_areas_city_status ON areas (city_code, status, name_key);

CREATE TABLE area_pincodes (
    area_id         BIGINT            NOT NULL,
    pincode         CHAR(6)           NOT NULL,
    created_at      ${timestamp_type} NOT NULL,
    updated_at      ${timestamp_type} NOT NULL,
    CONSTRAINT pk_area_pincodes PRIMARY KEY (area_id, pincode),
    CONSTRAINT fk_area_pincodes_area FOREIGN KEY (area_id) REFERENCES areas (id)
);
CREATE INDEX ix_area_pincodes_pincode ON area_pincodes (pincode);
```

### 3.2 `societies`

```sql
CREATE TABLE societies (
    id              BIGINT            NOT NULL,
    public_id       CHAR(36)          NOT NULL,
    area_id         BIGINT            NOT NULL,
    city_code       VARCHAR(8)        NOT NULL,   -- copy of the area's city, for city-wide browse
    name            VARCHAR(160)      NOT NULL,
    name_key        VARCHAR(160)      NOT NULL,
    developer       VARCHAR(120),                 -- e.g. "Sobha"
    kind            VARCHAR(24)       NOT NULL,   -- GATED_COMMUNITY | APARTMENT_COMPLEX
    street          VARCHAR(200),
    status          VARCHAR(16)       NOT NULL,   -- ACTIVE | PENDING | HIDDEN
    created_by      BIGINT,
    is_demo         BOOLEAN           NOT NULL DEFAULT FALSE,
    created_at      ${timestamp_type} NOT NULL,
    updated_at      ${timestamp_type} NOT NULL,
    CONSTRAINT pk_societies PRIMARY KEY (id),
    CONSTRAINT uq_societies_public_id UNIQUE (public_id),
    CONSTRAINT uq_societies_area_name UNIQUE (area_id, name_key),
    CONSTRAINT fk_societies_area FOREIGN KEY (area_id) REFERENCES areas (id),
    CONSTRAINT fk_societies_city FOREIGN KEY (city_code) REFERENCES cities (code),
    CONSTRAINT fk_societies_created_by FOREIGN KEY (created_by) REFERENCES users (id)
);
CREATE INDEX ix_societies_city_status ON societies (city_code, status, name_key);
```
Browse by area uses the unique `(area_id, name_key)` index as its prefix index.

```sql
CREATE TABLE society_towers (
```

### 3.4 `properties` additions

```sql
ALTER TABLE properties ADD COLUMN area_id    BIGINT REFERENCES areas (id);
ALTER TABLE properties ADD COLUMN society_id BIGINT REFERENCES societies (id);
ALTER TABLE properties ADD COLUMN tower_id   BIGINT REFERENCES society_towers (id);
ALTER TABLE properties ADD COLUMN wing_id    BIGINT REFERENCES society_wings (id);
CREATE INDEX ix_properties_area_status ON properties (area_id, status);
CREATE INDEX ix_properties_society_status ON properties (society_id, status, tower_id, wing_id);
```
- Nullable in the DDL: SQLite cannot add a `NOT NULL` column without a default, and a column with `REFERENCES` must default to null. The API requires `area_id` (D-110).
- Placement rules (`wing ⇒ tower ⇒ society ⇒ area ⇒ city`) are checked in the service layer (`422 location_mismatch`), because a portable `CHECK` cannot look at other tables.
- `locality`, `locality_key` and `pincode` stay (V1 columns and index `ix_properties_city_status_locality`); the API copies `locality` from the area name.
- Existing index `ix_properties_landlord (landlord_id, status)` serves the owner portfolio (D-113).

### 3.5 Queries the indexes serve

| Screen / endpoint | Query shape | Index |
|---|---|---|
| Area lookup by PIN code (`GET /areas?pincode=`) | `area_pincodes WHERE pincode = ?` | `ix_area_pincodes_pincode` |
| Area lookup by name (`GET /areas?city=&q=`) | `areas WHERE city_code = ? AND status = 'ACTIVE' AND name_key LIKE ?%` | `ix_areas_city_status` |
| Browse societies in a city / area | `societies WHERE city_code = ? AND status = 'ACTIVE'` or `WHERE area_id = ?` | `ix_societies_city_status`, `uq_societies_area_name` |
| Society page homes, per tower / wing | `properties WHERE society_id = ? AND status = 'PUBLISHED'` | `ix_properties_society_status` |
| Area page, standalone homes | `properties WHERE area_id = ? AND status = 'PUBLISHED' AND society_id IS NULL` | `ix_properties_area_status` |
| Owner portfolio | `properties WHERE landlord_id = ? AND status = 'PUBLISHED'` | `ix_properties_landlord` |
| Rating card for any subject | `rating_aggregates WHERE subject_type = ? AND subject_id = ?` | `pk_rating_aggregates` |
| Top-rated societies / areas | aggregates `WHERE subject_type = 'SOCIETY'` ordered by `bayes_score`, joined to the city's societies | `ix_rating_aggregates_rank` |
| Society reviews (`/societies/{id}/reviews`) | `reviews JOIN properties ON property_id WHERE society_id = ? AND direction = 'TENANT_TO_PROPERTY' AND status = 'PUBLISHED'` | `ix_properties_society_status` + `ix_reviews_property` |
| Roll-up recompute (D-111) | same review join per society / area / owner | same as above + `ix_properties_landlord` |
| Duplicate PAN / phone | `identity_verifications WHERE method = ? AND value_hmac = ?` | `ix_identity_verifications_hmac` |
| Admin identity queue | `WHERE status = 'PENDING' AND method = ? ORDER BY created_at` | `ix_identity_verifications_queue` |
| OTP send limits | `phone_otp_challenges WHERE user_id = ? AND created_at > ?` (and by `phone_hmac`) | `ix_phone_otp_user_created`, `ix_phone_otp_phone_created` |

### 3.6 MySQL vendor file

MySQL parses but ignores column-level `REFERENCES` in `ALTER TABLE … ADD COLUMN`. `db/vendor/mysql/V<n>_1__location_fks.sql` (same `<n>` as the location migration) adds:
```sql
ALTER TABLE properties ADD CONSTRAINT fk_properties_area    FOREIGN KEY (area_id)    REFERENCES areas (id);
ALTER TABLE properties ADD CONSTRAINT fk_properties_society FOREIGN KEY (society_id) REFERENCES societies (id);
ALTER TABLE properties ADD CONSTRAINT fk_properties_tower   FOREIGN KEY (tower_id)   REFERENCES society_towers (id);
ALTER TABLE properties ADD CONSTRAINT fk_properties_wing    FOREIGN KEY (wing_id)    REFERENCES society_wings (id);
```
The file lives outside `db/migration`, because Flyway scans every location recursively and a file under `db/migration` would run on SQLite too. The B15 PR sets `spring.flyway.locations` to `classpath:db/migration,classpath:db/vendor/{vendor}` (D-10), so only MySQL loads `db/vendor/mysql`; on SQLite and Postgres the `_1` version simply does not exist.

## 4. Rating roll-ups (D-111)

`rating_aggregates` (V1) gets three new `subject_type` values; same columns, same recompute-from-source rule (D-33).

| `subject_type` | `subject_id` | Source reviews |
|---|---|---|
| `LANDLORD`, `TENANT` | user id | person reviews (unchanged) |
| `PROPERTY` | property id | `TENANT_TO_PROPERTY` of that property (unchanged) |
| `SOCIETY` | society id | `TENANT_TO_PROPERTY` of published properties with that `society_id` |
| `AREA` | area id | `TENANT_TO_PROPERTY` of published properties with that `area_id` |
| `OWNER_HOMES` | landlord user id | `TENANT_TO_PROPERTY` of published properties with that `landlord_id` |

Only reviews with `status = 'PUBLISHED'` and `counts_in_aggregate = true` count. Tower and wing numbers are computed at read time.
